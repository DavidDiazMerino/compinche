# Compinche

### From their hands to yours.

**An apprentice that watches someone cook, asks about what they didn't explain, and teaches it back to you in your own kitchen.**

Recipes leave things unsaid: “a little more”, “until it looks right”, “like that”. The knowledge is in the person: what they look at, why they turn the heat down, how they know it's ready.

Compinche watches a cook through a phone camera (or Ray-Ban Meta glasses through the Wearables SDK). When the cook makes a decision without saying why, it asks, out loud, at that moment. The cook's own words are kept as a card, tied to the question and to the moment in the video. The cook confirms or corrects the card. Later, when someone else makes the dish in another kitchen, Compinche brings that teaching back, and only that.

The demo is personal: my dad teaching me his béchamel for croquettes.

## The loop

1. **Watch.** Muse Spark looks at the latest frames while the person cooks. It follows the phases of the recipe and the heat.
2. **Ask.** When it sees a decision whose reason is missing (lowering the heat, lifting the whisk to look, covering the bowl), it asks one short question aloud and waits for a natural pause.
3. **Keep their words.** The spoken answer is transcribed by Muse Voice Transcribe. Spark checks whether it explains the question: an unrelated reply keeps the question open, and a fragmented answer is joined first. The card keeps the speaker, the question, the frames and the moment in the video. The literal words are never rewritten.
4. **Review.** The cook confirms the card, or corrects it in their own words. A correction replaces whatever had been derived from the earlier words. Muse Glimmer, running locally (Spark if it is not running), turns each explanation into a titled card in the background.
5. **Teach it back.** In learner mode, Compinche uses **only confirmed cards**:
   - It answers questions by quoting the teacher, and says so when something was not taught.
   - It gives one proactive reminder when the learner reaches the right moment.
   - It measures the learner's pan and compares it with the one in the lesson.
   - It compares the learner's gesture with the teacher's demonstration.

## Meta models

| Model | What it does in Compinche | Where it runs |
| --- | --- | --- |
| **Muse Spark 1.3** | Watches and asks, checks whether an answer explains the question, guides the learner, compares gestures | Meta Model API |
| **Muse Voice Transcribe 1.0** | Continuous speech recognition, biased with the recipe's vocabulary | Meta Model API (WebSocket) |
| **SAM 3.1** | Segments the vessel, the scale reference and the tool in use | Meta Model API |
| **Muse Glimmer 30B** | Turns explanations into cards in the background; optionally answers the learner | Local GPU (vLLM, FP8), Spark as fallback |
| **MapAnything** (Apache-2.0) | Metric geometry for measuring | Local GPU |
| **CoTracker3** | Point tracking to align gestures | Local GPU |

## Run it

Use **Python 3.12** and a recent Chrome. Node.js 18+ is only needed for the npm shortcuts. There is no frontend build step.

```bash
git clone https://github.com/DavidDiazMerino/compinche.git
cd compinche
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.lock.txt
cp backend/.env.example backend/.env.local     # add MODEL_API_KEY
backend/.venv/bin/python -m backend.serve --env-file backend/.env.local --port 8017
```

Open **[http://127.0.0.1:8017/#teach](http://127.0.0.1:8017/#teach)**:

- **Teach:** choose the phone camera or a recording, say who is cooking, and start. Compinche watches, listens and asks. The **Glasses view** button gives a clean frame for filming.
- **Learn:** choose a lesson; only its confirmed cards are used.

Optional parts:

- **Muse Glimmer:** run `backend/glimmer/serve.sh`, then start the server with `COMPINCHE_GLIMMER_URL=http://127.0.0.1:8100/v1`.
- **Measurement and gestures:** need a local GPU runtime; see [backend/MEASURE.md](backend/MEASURE.md).
- **Local voice:** Piper; see [docs/LIVE.md](docs/LIVE.md#instalación-y-api). Without it, the browser voice is used.

**Phone camera:** browsers only allow the camera on HTTPS or `localhost`.

- Over USB: `adb reverse tcp:8017 tcp:8017` and open `http://localhost:8017/#teach` on the phone.
- From another house: put it behind Tailscale with `tailscale serve`, and add the host name to `COMPINCHE_ALLOWED_HOSTS`. The app has no accounts, so anyone in that tailnet can open it.

**Keys:** the Meta key stays in the server environment (`MODEL_API_KEY`), never in the browser. `backend.serve --env-file` loads a local file that Git ignores.

## How it works

```mermaid
flowchart LR
    Cam["Phone camera, replay<br/>or glasses (SDK)"] -->|"frames"| Vision["Spark: watch<br/>(one in flight, one pending)"]
    Mic["Microphone"] -->|"PCM 24 kHz"| ASR["Muse Voice Transcribe"]
    Vision --> Gap{"Unexplained<br/>decision?"}
    Gap -->|"question"| Voice["Local voice (Piper)"]
    ASR --> Check["Spark: does the answer<br/>explain it?"]
    Check -->|"yes"| Card["Card: their words, question,<br/>frames, moment"]
    Card --> Glimmer["Glimmer (local):<br/>title and category"]
    Card --> Review["Cook confirms or corrects"]
    Review --> Lesson["Confirmed lesson"]
    Lesson --> Learner["Learner mode: answers,<br/>reminders, pan, gesture"]
    Vision -.-> Tools["SAM 3.1 + MapAnything: measure<br/>CoTracker3: gesture"]
```

Vision, speech, voice and the slow tools (measurement, gestures, card consolidation) run in separate queues, so a slow tool never delays a question. Vision keeps one observation in flight and one replaceable pending one, rather than queueing every late frame. Seeking, pausing or stopping invalidates stale results, and late questions say which moment they refer to. Recorded audio from a replay is context only: it can never answer a question in someone's name.

Each card separates what was **said** (the literal quote, with its audio) from what was **derived** (signal, decision, title). Only a person can confirm it.

The learner never sees unconfirmed cards. A learner answer marked as known must cite a confirmed card. Quantities that are not in the lesson are refused rather than made up.

Code: [backend/live.py](backend/live.py) (session coordinator), [backend/live_provider.py](backend/live_provider.py) (prompts and Meta adapters), [backend/measure.py](backend/measure.py), [backend/gesture.py](backend/gesture.py), [dist/live.js](dist/live.js) (live interface).

## Architecture

### Components

```mermaid
flowchart TB
    subgraph Client["Browser or Android host"]
        UI["Live UI (dist/live.js)<br/>camera · replay · glasses view"]
        Cap["Frame sampler<br/>1 fps, sends on change"]
        Mic["Mic → PCM16 24 kHz"]
        Play["Voice player<br/>(playback ack)"]
    end
    subgraph Server["FastAPI server (backend/)"]
        Coord["Live coordinator<br/>backend/live.py"]
        VQ["Vision queue<br/>1 in flight + 1 pending"]
        AQ["Speech: WebSocket relay<br/>WAV fallback"]
        TQ["Slow tools queue<br/>measure · gesture · cards"]
        Store[("SQLite + local media<br/>backend/.data, git-ignored")]
        Piper["Piper TTS (local)"]
    end
    subgraph Meta["Meta Model API"]
        Spark["Muse Spark 1.3<br/>watch · ask · check · guide"]
        ASR["Muse Voice Transcribe 1.0"]
        SAM["SAM 3.1"]
    end
    subgraph GPU["Local GPU (GB10)"]
        Glimmer["Muse Glimmer 30B<br/>vLLM, FP8"]
        Worker["Resident worker<br/>MapAnything + CoTracker3"]
    end
    Cap -->|"2 JPEG + video time"| VQ --> Spark
    Mic -->|"stream"| AQ --> ASR
    Spark --> Coord
    ASR --> Coord
    Coord -->|"question / guide"| Piper --> Play
    Coord --> Store
    Coord --> TQ
    TQ --> SAM
    TQ --> Worker
    TQ --> Glimmer
    Coord -->|"SSE snapshot"| UI
```

Each kind of work has its own queue, so a slow tool never delays a question. Vision keeps one call in flight and one replaceable pending window: when the model is slow, it skips stale frames rather than falling behind. Everything carries the **video time** of the frames it came from, so a late answer still points at the right moment.

### One question, end to end

```mermaid
sequenceDiagram
    participant C as Camera / replay
    participant S as Server (coordinator)
    participant M as Muse Spark
    participant V as Piper voice
    participant P as Person
    participant T as Voice Transcribe
    C->>S: 2 frames + video time (admission ~17 ms)
    S->>M: observe: phase, heat, decision without a reason?
    M-->>S: observation + gap (p50 3.1 s)
    S->>S: is it worth asking? same gap asked already? is someone talking?
    S->>V: question text
    V-->>P: spoken question (ready → playback ~0.23 s)
    P->>T: answer, streamed
    T-->>S: final transcript
    S->>M: does it explain the question?
    M-->>S: yes → card (literal quote + audio + frames)
    S->>S: Glimmer titles the card in the background (~65 s)
    P->>S: cook confirms or corrects
```

### Question lifecycle

```mermaid
stateDiagram-v2
    [*] --> pending: gap seen, nobody talking
    pending --> spoken: playback started (client ack)
    pending --> expired: newer candidate / context moved on
    spoken --> answered: answer explains it
    spoken --> spoken: unrelated reply (stays open)
    spoken --> expired: relevance window elapsed
    answered --> [*]: card, waiting for review
    spoken --> superseded: the learner asked something else, or a comparison replaced it
```

Guides in learner mode follow the same path, with one more rule: each confirmed card is used for at most one reminder.

### The two journeys

```mermaid
journey
    title Teaching (Dad) and learning (me)
    section Teacher cooks
      Cooks as usual, phone or glasses watching: 5: Teacher
      Hears a short question at a natural pause: 4: Teacher
      Answers in their own words: 5: Teacher
      Confirms or corrects the card with their name: 4: Teacher
    section Learner cooks
      Picks the lesson, cooks in their own kitchen: 5: Learner
      Asks out loud; gets the teacher's words back: 5: Learner
      Gets a reminder just before the step: 4: Learner
      Repeats the gesture; sees it next to the teacher's: 4: Learner
```

## Latency: what we measured

From the stored sessions, not from the video. *Teach* is Dad's 16-minute recording in causal replay (3 Nov, 145 frame windows, 12 questions). *Learn* is my own recording in learner mode (4 Nov, 96 windows, 7 guides).

| Step | Teach p50 / p90 | Learn p50 / p90 |
| --- | --- | --- |
| Frames admitted by the server | 17 / 21 ms | 8 ms |
| Waiting in the vision queue | 6 ms / 0.84 s | 1.8 / 3.5 s |
| Muse Spark observation (`minimal` effort, 2 frames) | 3.1 / 5.6 s | 4.3 / 5.6 s |
| Observation → question or guide ready | 15 ms (same call) | 2.4 / 3.1 s (second Spark call that writes the guide from the card) |
| Frames received → question ready | **7.3 / 9.7 s** | **7.7 / 8.7 s** |
| Question ready → voice playing (client ack) | 0.23 / 0.29 s | 0.29 / 0.38 s |
| Speech: streamed transcript | real time (WebSocket) | real time |
| Speech: WAV fallback per utterance | — | 2.6 s |
| SAM 3.1 (Meta API) + MapAnything (warm) | 0.8–1.4 s + 0.2–1.6 s | 1.1–8.6 s for the whole measurement |
| CoTracker3 per 10 s clip (warm) | — | 2.9–8.9 s |
| Glimmer card in the background | ~65 s | — |

Read it like this: a question is spoken about **7–10 s after the frames that triggered it**, plus the capture interval (frames are sampled every second and sent when the scene changes, at least 4 s apart). That is fast enough for slow decisions (the heat, the texture of the batter), which last for minutes. It is too slow for a two-second gesture, so questions about a gesture are phrased about what just happened (“When you lifted the whisk just now…”). The wait is also partly deliberate: Compinche never talks over the cook, and it holds a question until there is a pause.

On the omelette video the same Spark call took 2.6 / 3.8 s (p50 / p90): shorter scenes, shorter observations.

### How we would make it faster

1. **Send frames on events, not on a timer.** A cheap local motion or hand detector (or the SAM 3.1 masks we already compute) would send the window the moment the tool leaves the pot, rather than at the next interval. That alone removes up to 4 s.
2. **Stream Spark's structured output.** Today we wait for the whole JSON. The question field could be spoken as soon as it is complete and validated, while the rest of the observation finishes.
3. **Split observing from asking.** Run a small, fast “is something happening?” pass on every window and only call the full observation when it fires. Glimmer is too slow for this on our GPU (~7.5 tokens/s); a smaller open model, or Glimmer with speculative decoding, are the candidates we would measure next.
4. **Pre-write the guide.** In learner mode, the second Spark call (2.4 s) could be prepared as soon as the learner enters the phase where a card applies, and only spoken when the moment arrives.
5. **Keep everything warm.** Measurement's slow cases (8.6 s) are a cold worker; the worker is resident now and starts with the session.

Every one of these needs measuring on annotated opportunities (missed, duplicate and late questions too), not only on the questions that worked.

## Error recovery

Compinche is built to say “I don't know” rather than guess:

- **No reference to measure with.** If SAM 3.1 finds the vessel but no object of known size, Compinche asks “How wide is it across?” instead of giving a number. If the view is too steep, it asks for a view from above. A stated size outside 8–80 cm is not accepted, and inches are converted.
- **An answer that doesn't answer.** Spark checks whether the reply explains the question. An unrelated reply leaves the question open; a reply split across several utterances is joined first.
- **Not in the lesson.** A learner answer marked as known must cite a confirmed card. Otherwise Compinche says the teacher didn't explain it. Quantities that are not in the lesson are refused, across languages (“a litre” vs “un litro”).
- **A model call fails.** Vision failures are logged with their cause and the session carries on with the next window. If Glimmer is not running or times out, Spark writes the card.
- **Stale results.** Seeking, pausing or stopping bumps a scene epoch, and results from the old epoch are dropped. A question about a moment that has passed expires instead of being asked late.
- **Gesture clips that are too short.** Below six frames per side, no comparison is made.
- **Recorded voices are never answers.** In a replay, the recording's own audio is context only. It can never answer a question in the recorded person's name.
- **Flame cues on induction.** The flame-based heat reading only runs when a gas flame was seen first, so an induction hob's lights are not read as fire.

## Tried on another recipe

To check that Compinche is not built for croquettes, we ran a **Spanish omelette** video through teach mode with the same code and prompts: [Patata tortilla.webm](https://commons.wikimedia.org/wiki/File:Patata_tortilla.webm) by Elene B, CC BY-SA 4.0, 2:39. The video is not in this repository.

It followed the recipe from the frames alone: peeling and cutting potatoes, potatoes into cold oil, frying, draining onto paper, cracking and beating eggs, mixing, the mixture into the hot pan, the flip, plating. It asked three questions:

| Video | Question |
| --- | --- |
| 0:01 | “I see your golden Spanish omelette ready on the counter. What did you put in it and how much of each?” (mise en place; the video opens on the finished dish) |
| 1:17 | “I can't see anything of a known size to measure the pan. How wide is it across?” |
| 2:37 | “When you tipped it out, how did you know it was ready to come out?” |

Three questions in 2:39 is fewer than on Dad's recording (12 in 16 min, a similar rate, but this video is an edited montage with cuts, so fewer decisions are left unexplained on screen). Nobody answered, so no cards were made. The summary is in [docs/experiments/2026-11-04-other-recipe](docs/experiments/2026-11-04-other-recipe/summary.json).

## The demo video: what is live and what is edited

We would rather say it than have someone find it:

- **Every Compinche line is real output.** The questions, answers, reminders and comparisons in the video were produced by the app in two sessions: Dad's 16-minute recording in causal replay (teach), and my own recording of making béchamel replayed in learner mode with Dad's four cards. Those sessions were run from recordings, not with a live phone in the kitchen; a live phone session was tested separately on 3 Nov.
- **Dad answered afterwards.** He couldn't cook again, so he answered the app's questions by voice notes. The notes were attached to those questions in the app, and the cards were confirmed with his name.
- **Two bubbles were moved in the edit.** The film question (scene 08) appears about 5 s earlier than it did, so that it is on screen while he handles the film. In my kitchen, the heat reminder came about 25 s before I lowered the heat. In the edit it sits right before the gesture.
- **The gesture split screen** was computed after the session, with the app's own `GestureService`, on the moments the app picked. The live trigger was cancelled because my recording ended first.
- **The phone setup** at the start is the real interface, recorded in a phone-sized browser window. The “under the hood” shots are the real SAM 3.1 masks, MapAnything point cloud, CoTracker3 tracks and timeline from these sessions.
- **The pot size** (about 29–31 cm) has not been checked against a tape measure.

## Limits

- **One teacher, one learner, one dish so far.** The full loop (questions, answers, confirmed cards, guidance in another kitchen) has been run end to end once, with Dad and me. The omelette run only covers teach mode without answers.
- **Vessel diameter is an estimate with a range.** It needs a visible reference of known size (or the cook stating the size). It does not validate the recipe: the advice is geometry only.
- **Gesture comparison names one visible difference.** It does not judge doneness, texture or temperature.
- **No weights, temperatures or doneness.** Compinche does not infer them from images.
- **Latency.** A question arrives 7–10 s after the frames that triggered it (see [Latency](#latency-what-we-measured)). That suits slow decisions, but it is too slow to ask about a short gesture while it is still happening.
- **Local development server.** Keep it on `127.0.0.1` or inside a private network: there are no accounts or authorisation.

## Data and privacy

Family recordings and their frames stay in local storage that Git ignores (`backend/.data/`). They are not in this repository. Each live session starts with explicit consent. Frames and audio from that session are sent to the Meta Model API with `store:false`. Glimmer, MapAnything, CoTracker3 and the voice run locally.
